# Commissioning prompt

Use this when handing a council brief to a builder. The earlier version referred to an attachment that never arrived, asked for verification of "legal authorities" without saying whose, and allowed the builder to mint before anyone had agreed on the design. This version fixes those three things.

---

I am commissioning six enduring specialist agents for the Dream Teams Expert Council, to live in the Agent Office Ring.

The design brief is at `docs/council/EXPERT_COUNCIL.md` in `appl044/agent-office-ring`. If I attach a newer directive, its path is written in the first line of this message. If no path is there, there is no attachment, and the brief in the repository is the whole brief.

Treat the brief as intent, not as a specification. You may challenge it, improve it, and propose better methods. Keep its mission and its boundaries: advice only, no action on law, money, publication, or deployment; fiction and record kept in separate files; human approval for every Tier 3 change.

Before minting anything, return four things in one message:

1. The architecture you will build, with any change from the brief marked and explained.
2. The disagreements, each tied to the line in the brief it disputes.
3. The sequence, one member first, with the step at which I say "mint".
4. The acceptance criteria, stated so that I can check them on the dashboard and in the repository without your help.

Verify before you assert. For each claim about what the Cursor Cloud Agents API, the ring, or a model can do, name the call you made or the file you read. For each source in a member's knowledge file, confirm it resolves. For each legal statement, name the statute, rule, or guidance and its date, and mark it advisory.

Do not mint until I write "mint 1". Do not create keys. Do not push to main. Do not put a real person's health information in any file.

Build these to be good colleagues now and better colleagues in ten years. The person is the folder. The model is this year's engine.
